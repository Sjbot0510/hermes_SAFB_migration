3. NUMERICAL BEHAVIOR & LOGIC VERIFICATION
------------------------------------------------------------

No formal cross-validation against the Python reference has been
performed in this session.  The C code was translated by inspection
following the PYTHON_REFERENCE_MAP.md.  However, the following
behaviors have been observed that appear correct:

  - Fraction arithmetic: frac_new(), frac_mod1(), frac_to_float()
    match Python's fractions.Fraction behavior for positive and
    negative values.
  - Metric tensor inverse: cubic (a=b=c=1, α=β=γ=90) returns identity
    matrix to within floating-point precision.
  - q² calculation: for cubic a=b=c=1, HKL={1,0,0} yields q²=1.0,
    matching Python's numpy-based computation.
  - Lattice roundtrip: lattice_params_from_basis(direct_basis_from_lattice_info(...))
    recovers original parameters to ~1e-15 relative error.
  - Star generation: 4-fold symmetry correctly produces 4 vectors.
  - Amplitude sqrt scaling: sqrt(A/multiplicity) computed correctly.
  - Basis for P1: 3 modes ({-100}, {0-10}, {00-1}), each multiplicity 1,
    star_close=0.
  - Basis for Ia-3d: 5 modes ({000}, {400}, {800}, {1200}, {1600})
    with correct q² values.

Known discrepancy / difference in approach:
  - The C code uses stack-allocated SAFBBasis (passed by pointer)
    with inline Star[MAX_MODES] arrays, while Python uses dataclass
    instances with list/tuple collections.  This is a structural
    difference but does not affect numerical output.
  - The C RNG is a custom xorshift64; Python uses numpy's Mersenne
    Twister.  Random initializers produce different sequences (expected).

Bug / Crash (1):
  initializers test: test_file_initialization() crashes with SIGSEGV
  (signal 139 = 128+11).  The crash occurs during the second call to
  file_initialization() (the "diff lattice, no P" case).  The first
  call with NULL lattice info and NULL P matrix completes
  successfully.

  Likely cause: file_initialization() receives a non-NULL
  read_lattice_info with different lattice parameters but NULL P
  matrix.  The code path at lines 346-352 sets use_transform=1
  when lattices differ, but then checks P != NULL at line 355.
  However, the lookup_amplitude_from_data() and subsequent
  star->multiplicity access may dereference uninitialized or freed
  memory.  The ScatteringProfile may also have stale data from the
  first call if scattering_profile_free() is called too early.

  Recommended fix path:
  1. Add -g flag to Makefile and run under gdb to pinpoint the
     exact crash location.
  2. Check that family_planes_info() and read_scattering_data()
     return valid data in the second test case.
  3. Verify that out_coeffs array is large enough for both calls
     (tests reuse the same array).
